# 新生儿用品清单 & 宝妈用品清单 — 扩展开发指南

> 状态：**规划中（待确认后再开发）**
> 来源：基于用户提供的三张清单截图（超精简新生儿用品清单 / 超精简妈妈用品清单 / 2025 最全待产包清单）+ 通用母婴知识整理归纳。
> 注：两个小红书参考链接因登录墙/网络策略无法直接抓取，内容以截图与通用知识为准，正式上架前建议再人工校对。

---

## 1. 背景与目标

现有「待产包清单」（工具页，`list_key = hospital_bag`）定位是**入院当天必备**，条目较精简。
用户希望新增两个**覆盖「孩子出生前就备好、可用到产后第一年」**的更全清单：

1. **新生儿用品清单**（0–12 个月）
2. **宝妈用品清单**（产后 / 月子 / 哺乳期恢复）

关键诉求：
- 比待产包**更详细、时间跨度更长**（不止待产，含后续一年）。
- 分类多 → **工具内部要再分子类**（喂养 / 消耗 / 衣物 / 洗护 / 出行 …）。
- 每个条目最好带**建议数量**与**准备时机**（产前 / 月子 / 3M+ / 6M+ / 按需），方便用户分阶段囤货。

---

## 2. 与现有「待产包清单」的关系（冲突处理）

三份清单**会有重叠**（如奶瓶、纸尿裤、产褥垫等待产包里有，新生儿/宝妈清单里也有）。处理原则：

- **三者定位不同，允许重叠，不强行去重：**
  - `hospital_bag`（待产包）= 入院当天拎走的**精简子集**。
  - `newborn`（新生儿）= 第一年**全量**，重叠项用 `timing=产前` 标注（≈ 待产时就要备）。
  - `mom`（宝妈）= 产后恢复**全量**，同样用时机标签区分。
- 用 **`timing` 标签**让用户自行判断「现在该不该买」，而不是把同一件东西藏在三个互斥列表里找不到。
- **开放问题（见第 8 节）**：是否要做「待产包 = 新生儿/宝妈清单中 timing=产前 项的视图」这种联动，留待确认；MVP 先做成三个独立清单。

## 3. 数据模型与数据库迁移

### 3.1 复用并泛化现有 `checklist_items` 表

现有表（v4）：`checklist_items(cl_id, category, title, is_checked)`，仅服务待产包。
**泛化为多清单**：加 `list_key` 区分属于哪个工具，加 `qty` / `timing` / `sort` 丰富信息。

### 3.2 迁移 v5（`DatabaseService.dbVersion = 5`，在 `_migrations` 加一条）

```sql
ALTER TABLE checklist_items ADD COLUMN list_key TEXT NOT NULL DEFAULT 'hospital_bag';
ALTER TABLE checklist_items ADD COLUMN qty      TEXT;     -- 建议数量,如 "2条"
ALTER TABLE checklist_items ADD COLUMN timing   TEXT;     -- 准备时机标签
ALTER TABLE checklist_items ADD COLUMN sort     INTEGER NOT NULL DEFAULT 0;
-- 然后 batch 注入 newborn / mom 两套模板(见第 6 节)
```

- SQLite 支持 `ALTER TABLE ADD COLUMN`；存量待产包行自动得到 `list_key='hospital_bag'`，零数据丢失。
- **新装用户**：`onCreate` 会顺序跑到 v5，三套模板都注入。
- **老用户**：`onUpgrade` 只跑 v5，给老表加列 + 注入两套新模板。

> ⚠️ 注意：v4 的待产包种子在 v4 迁移里注入；v5 只补 `newborn`/`mom`，不要重复注入待产包。

### 3.3 模型 `ChecklistItem` 扩展

```dart
class ChecklistItem {
  final int? id;
  final String listKey;   // hospital_bag / newborn / mom
  final String category;  // 子类,如 "喂养类"
  final String title;
  final String? qty;      // "2条"、"3-5件" 等,可空
  final String? timing;   // "产前"/"月子"/"3M+"/"6M+"/"按需",可空
  final bool checked;
  // toMap/fromMap/copyWith 同步增加这些字段
}
```

## 4. UI / 交互设计

### 4.1 工具页（`tools_screen.dart`）

在现有「待产包清单」下方再加两个入口：

| emoji | 标题 | 副标题 |
|---|---|---|
| 🍼 | 新生儿用品清单 | 0–1 岁全清单,按时机分阶段备齐 |
| 🤱 | 宝妈用品清单 | 产后 / 月子 / 哺乳,恢复用品一站备 |

（待产包保留不变。）

### 4.2 通用清单页（重构 `checklist_screen.dart` 为可复用组件）

把现有 `ChecklistScreen` 泛化为接收参数：

```dart
ChecklistScreen({
  required String listKey,
  required String title,        // AppBar 标题
  required List<String> categoryOrder, // 子类显示顺序
})
```

页面结构（从上到下）：
1. **顶部进度卡**：总进度条 `已备 X / Y 项` + 一句时机提示。
2. **时机筛选 chips**（可选增强）：`全部 / 产前 / 月子 / 3M+ / 6M+`，点选过滤。
3. **按子类分组的卡片**（每个 `category` 一张 `SectionCard`）：
   - 卡头：子类名 + 该类进度（如 `3/8`）+ ➕ 添加按钮。
   - 条目行：复选框 + 标题 +（灰色小字）数量 +（小标签）时机；左滑删除。
4. 复用现有勾选/增删交互与 `AppState` 写库逻辑（扩展为按 `listKey` 过滤）。

### 4.3 AppState / DatabaseService 调整

- `DatabaseService.getChecklist(String listKey)` → `WHERE list_key = ?`。
- `AppState`：`checklistFor(listKey)` getter；`addChecklistItem(listKey, category, title, {qty})`；`toggle/delete` 复用现有。
- 现有待产包页改为 `ChecklistScreen(listKey: 'hospital_bag', ...)`。

## 5. 实施步骤（分阶段，确认后执行）

1. **数据层**：模型扩字段 → v5 迁移（加列 + 注入两套模板）→ DatabaseService 按 listKey 查询。
2. **状态层**：AppState 按 listKey 暴露列表与增删改。
3. **UI 层**：泛化 ChecklistScreen（支持子类分组 + 时机标签 + 可选筛选）→ 待产包页切到新组件 → 工具页加两入口。
4. **测试**：ChecklistItem 新字段序列化用例；（可选）迁移 v4→v5 的字段默认值用例。
5. **文档**：README「已实现/工具」补两项；本指南标记为「已实现」。
6. **PR + CI 绿 + 合并**（main 已受保护，走 PR 流程）。

> 体量评估：纯增量，复用现有清单交互与迁移框架，风险低。预计 1 个 PR 完成。

## 8. 待确认的问题（开发前请拍板）

1. **三清单是否联动**：待产包是否做成「新生儿+宝妈清单中 `timing=产前` 项」的自动视图？还是保持三个完全独立、各自维护？（MVP 倾向**独立**）
2. **时机筛选 chips** 是否要做（`全部/产前/月子/3M+/6M+`）？还是先只按子类分组、不做筛选？
3. **数量字段**是否展示/可编辑，还是只作为模板默认文案？
4. 模板条目**取舍**：以上为「较全」版本，是否需要精简（参考截图「超精简」风格）或再加项？
5. 是否需要**「一键重置为模板」**（用户删乱了能恢复）？
